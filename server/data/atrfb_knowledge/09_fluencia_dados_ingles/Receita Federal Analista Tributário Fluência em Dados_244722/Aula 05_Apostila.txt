                                                    DEFINIÇÃO

                   Um banco de dados é uma coleção de dados relacionados.


Professor, essa definição é bastante genérica! É verdade! Se formos seguir essa definição, as palavras

 Propriedade #1: um banco de dados representa algum aspecto do mundo real – algumas
  vezes chamado de Minimundo ou Universo de Discurso. As mudanças no minimundo são
  refletidas no banco de dados;

Agora, muito cuidado! Alguns tratam dados e informações como sinônimos, mas em nosso
contexto são conceitos diferentes. Para entender o que é um banco de dados, é muito importante
saber a diferença entre essas duas palavras:

 Dados são fatos brutos, em sua forma primária – e, muitas vezes, os dados podem não fazer
  sentido sozinhos;

 Informações consiste no agrupamento de dados de forma organizada para fazer sentido e gerar
  conhecimento.

Galera, nós podemos afirmar que um banco de dados pode ter qualquer tamanho e
complexidade. Querem ver uns exemplos? Em relação à complexidade, uma lista telefônica pode
ser considerada um banco de dados com uma estrutura bem simples. Em relação ao tamanho, o
catálogo computadorizado de uma grande biblioteca pode conter meio milhão de livros
organizados sob diferentes categorias.

Um banco de dados de tamanho e complexidade ainda maior é mantido pela Receita Federal
para monitorar formulários de imposto de renda preenchidos pelos contribuintes. Se
considerarmos que existem 100 milhões de contribuintes e que cada um deles preenche uma média
de cinco formulários com aproximadamente 400 caracteres cada um, teríamos um banco de dados
de 100 x 106 x 400 x 5 caracteres (bytes) de informação.

Outra característica importante de um banco de dados é que ele pode ser gerado e mantido
manualmente, ou pode ser computadorizado. Por exemplo: um fichário com as fichas de papel
dos alunos de uma academia é um banco de dados que pode ser criado e mantido manualmente.
Um banco de dados computadorizado pode ser criado e mantido por programas desenvolvidos
especificamente para essa tarefa ou por um sistema gerenciador de banco de dados.

Pessoal, nos parágrafos anteriores, nós passamos direto por um conceito muito importante. Vocês
perceberam? Eu estou falando sobre o Sistema Gerenciador de Banco de Dados (SGBD)!

                                                                               DEFINIÇÃO

   Um sistema gerenciador de banco de dados é uma coleção de programas que permite
                   aos usuários criar e manter um banco de dados.


O SGBD é uma coleção de programas que facilita o processo de definição, construção,
manipulação, compartilhamento, proteção e manutenção de um banco de dados. Em detalhes:

1. Definição: processo que envolve especificar os tipos, estruturas e restrições dos dados a serem
   armazenados1;

2. Construção: processo que envolve armazenar os dados em algum meio controlado pelo sistema
   gerenciador de banco de dados;




1 Detalhe importante: a definição/descrição do banco de dados fica armazenada no próprio banco de dados na forma de um catálogo ou dicionário de dados – esses dados sobre o banco
de dados são chamados de metadados.

3. Manipulação: processo que inclui funções como consulta – para recuperar dados específicos;
   atualização – para refletir mudanças no minimundo; e geração de relatórios;

4. Compartilhamento: processo que permite que diversos usuários e programas acessem um
   banco de dados simultaneamente;

5. Proteção: processo que inclui a proteção do sistema contra defeitos (ou falhas) de hardware ou
   software, e proteção de segurança contra acesso não autorizado ou malicioso;

6. Manutenção: processo que permite a evolução à medida que os requisitos mudam com o
   tempo, uma vez que um banco de dados pode ter um ciclo de vida de muitos anos.

Por meio de Sistemas Gerenciadores de Bancos de Dados, os dados podem ser compartilhados, a
redundância pode ser controlada, inconsistências podem ser evitadas, a integridade dos dados
pode ser mantida, a segurança pode ser aperfeiçoada, requisitos conflitantes podem ser
balanceados, padrões podem ser utilizados e há suporte e controle de transações/usuários
concorrentes. Enfim... há diversas vantagens na sua utilização!

Características de Banco de Dados
                                                                                       INCIDÊNCIA EM PROVA: baixa


Nos dias atuais, nós utilizamos uma abordagem de banco de dados para salvaguarda e consulta de
dados. No entanto isso era feito por meio de arquivos esparsos antigamente. Arquivos? Sim!
Imaginem duas áreas que compõem uma escola: departamento financeiro e departamento
pedagógico. O primeiro cuida de mensalidades e pagamentos, e o segundo cuida das notas de
provas, médias e outras avaliações. Vocês sabem como era a abordagem de arquivos nesse caso?

O departamento financeiro e o departamento pedagógico possuíam seus dados armazenados em
diversos arquivos e possuíam diversas aplicações que acessavam, consultavam e manipulavam
esses arquivos. Exemplo: o departamento financeiro possuía um arquivo de dados pessoais dos
alunos e outro arquivo de pagamentos de mensalidades dos alunos; já o departamento pedagógico
possuía um arquivo de dados pessoais dos alunos e outro arquivo de notas de provas.

Vocês já sacaram o problema, não é? Embora ambos os departamentos estejam interessados em
dados sobre os alunos, cada um mantém arquivos separados e programas para manipular esses
arquivos. Existe uma clara redundância de informações, o que resulta em desperdício de espaço
de armazenamento e em esforços redundantes para manter os dados comuns atualizados.
Vamos imaginar uma situação hipotética...

O aluno Renato da Costa mentiu a idade na hora de se matricular na escola: disse que tinha 15 anos,
mas ele tinha na verdade 18 anos! Ele decide contar a verdade e pede que seus dados cadastrais
sejam atualizados. Nesse caso, ele terá que ir até o departamento pedagógico e pedir para ajustar
sua data de nascimento e depois ir até o departamento financeiro e pedir para ajustá-la também.
Ou seja, nós desperdiçamos espaço e reduzimos nossa eficiência.

Quando utilizamos um banco de dados em vez de arquivos esparsos, um único repositório
mantém dados que são definidos uma vez e depois acessados por outras entidades. Outra coisa:
no sistema de arquivos, cada aplicação é livre para nomear os elementos dos dados
independentemente. Exemplo: o departamento de pessoal pode ter chamado os contatos
telefônicos de “TELEFONES” e o departamento financeiro pode ter chamado de “CONTATOS”.

Na abordagem de bancos de dados, os nomes ou rótulos de dados são definidos uma vez com o
mesmo nome, e utilizados repetidamente por consultas, transações e aplicações – nós vamos ver
isso com clareza mais à frente. Pessoal, vamos falar agora um pouquinho sobre as principais
características da abordagem de banco de dados versus a abordagem de processamento de
arquivos esparsos – são basicamente quatro:

                                  CARACTERÍSTICAS DA ABORDAGEM DE BANCO DE DADOS

Natureza de autodescrição de um sistema de banco de dados

A palavra “autodescrição” já dá a dica! Os bancos de dados não contêm apenas dados – eles
contêm também uma definição ou descrição completa da estrutura e restrições desses dados.
Então, se ele armazena uma tabela com dados sobre as notas de um aluno, ele também armazenará
os dados sobre essa tabela. Que dados, professor? Ele armazena qual o nome da tabela, o nome de
suas colunas, o tamanho de cada coluna, entre outros.




                                                                      ==219a34==




Vejam que a imagem acima não traz informações sobre os alunos, você não consegue ver nenhum
nome de aluno, nem idade, nada disso. A imagem acima traz informações sobre a tabela que
armazena dados de alunos. Os bancos de dados possuem um catálogo1 com informações de cada
tabela, sendo que as informações armazenadas no catálogo são chamadas de metadados, uma vez
que trazem dados sobre os dados.

Isolamento entre programas e dados, e abstração de dados

Vocês se lembram da imagem de algumas páginas atrás em que nós definimos Aplicações, SGBD e
Banco de Dados? Pois é, tudo separado bonitinho! No processamento de arquivos, as aplicações
eram misturadas com a estrutura de arquivos. É por essa razão que dizemos que há um
isolamento entre programas e dados. Se você modifica suas aplicações, não interfere nos dados;
se você modifica seus dados, não interfere nas aplicações. Prosseguindo...

Vocês sabem o que quer dizer abstração? Essa é uma palavra muito comum na área de tecnologia da
informação e é bom que vocês saibam responder de bate-pronto: abstração é a subtração de
detalhes. Como consequência, podemos concluir que quanto mais abstrato, menos detalhes; e
quanto menos abstrato, mais detalhes. A seguir temos uma imagem aérea da Catedral de Brasília.
Pergunta: qual delas é mais abstrata? Da direita! Por quê? Porque tem menos detalhes.

A característica que permite a independência de dados da aplicação e a independência da
operação da aplicação é chamada de abstração de dados. Um SGBD oferece aos usuários uma
representação conceitual de dados que não inclui muitos dos detalhes de como os dados são

A abstração é a base para se conseguir o isolamento entre programas e dados. Por quê? Porque a
aplicação não precisa de detalhes do SGBD – ela precisa apenas de uma interface. Pensando em
um exemplo mais grosseiro: quando você quer que os correios façam uma entrega para outra
pessoa, você não quer saber se eles vão enviar de carro, navio ou avião – você só precisa ter a
garantia de que a entrega seja realizada.

Suporte de Múltiplas Visões de Dados

Pessoal, eu falei para vocês que o banco de dados funciona como um repositório central de dados –
diferente dos arquivos. Dessa forma, é possível que várias aplicações tentem acessá-lo e cada
uma pode ter uma necessidade diferente. Imagine que uma determinada aplicação não precise
visualizar toooodos os dados – pode ser que ela precise acessar apenas alguns. Logo, nós podemos
afirmar que aplicações diferentes exigem pontos de vista ou visões diferentes do banco.

Uma visão (ou view) é, em geral, um subconjunto do banco de dados. Dessa forma, se você deseja
visualizar apenas uma parte dos dados de uma tabela, você pode criar uma visão personalizada
apenas para a sua aplicação ou para um conjunto de usuários. Eu sei que isso pode não estar tão
claro agora, mas ficará mais claro quando prosseguirmos com a teoria. Guardem apenas que um
banco de dados oferece suporte a múltiplas visões de dados.

Compartilhamento de Dados e Processamento de Transação

Um SGBD multiusuário é todo aquele SGBD que suporta que múltiplas aplicações – também
chamadas de usuários – acessem o banco de dados ao mesmo tempo. Galera, isso é essencial se o
dado para múltiplas aplicações estiver sendo mantido em um único banco de dados. O SGBD
precisa incluir um software de controle de concorrência para garantir que vários usuários
interajam simultaneamente com o banco de dados sem problemas.

Transações de Banco de Dados
                                                                                                      INCIDÊNCIA EM PROVA: ALTA


Transações de banco de dados são unidades lógicas de trabalho que envolvem uma ou mais operações
de acesso e modificação de dados, executadas de forma que o sistema mantenha a consistência e a
integridade das informações. Elas são fundamentais em ambientes multiusuário e críticos, como sistemas
bancários, reservas de passagens e comércio eletrônico, pois garantem que as ações ocorram do início
ao fim, sem falhas ou interferências parciais.

Esse conceito faz parte das propriedades ACID (Atomicidade, Consistência, Isolamento e Durabilidade),
que garantem a confiabilidade das transações em sistemas de banco de dados.


       (CEBRASPE / CAPES – 2024) As propriedades ACID de uma transação garantem
       atomicidade, confidencialidade, isolamento e durabilidade na sua execução.
       _______________________

       Confidencialidade não faz parte dessas propriedades, sendo um princípio da segurança da informação, não de transações em
       bancos de dados (Errado).




       (CEBRASPE / MPE-TO – 2024) As propriedades autenticidade, consistência, isolamento e
       durabilidade garantem confiabilidade às transações executadas em um banco de dados.
       _______________________
       Comentários: a propriedade mencionada como "autenticidade" está incorreta no contexto. As propriedades que garantem
       confiabilidade a transações são ACID: Atomicidade, Consistência, Isolamento e Durabilidade. Autenticidade é um princípio da
       segurança da informação (Errado).



Atomicidade
A atomicidade é a propriedade de bancos de dados que garante que uma operação seja executada por
completo ou não seja executada. Em outras palavras, a ideia da atomicidade é bem direta: ou a transação
acontece por inteiro ou não acontece nada. Simples assim! Se der qualquer problema no meio do
caminho, tudo o que já foi feito é cancelado — e o banco volta ao estado anterior, como se nada tivesse
acontecido. Quer um exemplo do dia a dia? Imagina que você está transferindo R$ 200 da sua conta para
a de um amigo. Essa transação envolve duas etapas:

▪    Tirar os R$ 200 da sua conta.
▪    Colocar os R$ 200 na conta do seu amigo.

Agora pense: o sistema consegue debitar da sua conta, mas trava antes de creditar na conta do seu amigo.
E aí? Dinheiro sumiu no limbo? Não pode, né? É aí que entra a atomicidade: se qualquer parte da
transação falhar, o sistema desfaz tudo — inclusive o débito na sua conta. Mais uma vez: ou tudo dá certo,
ou nada muda. Não existe “meio termo” em transações. E como o sistema faz isso? Usando logs de
transações — uma espécie de diário que registra cada passo da transação. Se o sistema “cair” no meio do
processo, ele consulta esse diário e sabe exatamente o que precisa reverter (rollback) para garantir que
o banco continue íntegro.

Isso vale tanto para falhas técnicas quanto para erros de digitação ou até mesmo para situações em que
o sistema detecta uma regra sendo violada (tipo tentar transferir mais do que o saldo disponível). Em
todos esses casos, o banco de dados automaticamente cancela tudo e garante que os dados não fiquem
pela metade. Para quem está desenvolvendo sistemas, isso é uma tranquilidade enorme. Em vez de

Consistência
Agora vamos falar de consistência, o “C” do famoso modelo ACID — aquele conjunto de princípios que
garante que as transações em banco de dados sejam seguras, confiáveis e não virem uma bagunça.
Enquanto a atomicidade cuida de garantir que a transação aconteça toda ou não aconteça nada, a
consistência entra em cena para garantir que — depois da transação — o banco continue em um estado
válido, ou seja, sem dados malucos, incoerentes ou quebrando regras.

Vejam bem: o banco de dados tem um conjunto de regras que precisa seguir. Essas regras não caem do
céu — elas são definidas por quem projetou o banco. Estamos falando de chaves primárias, chaves
estrangeiras, restrições de domínio, gatilhos, validações de negócio... enfim, é tipo um “manual de boas
práticas” que o banco precisa respeitar o tempo todo.

Agora imagina um exemplo simples: um sistema de estoque com a regra de que o saldo de um produto
nunca pode ser negativo. Aí vem alguém e tenta registrar a venda de 10 unidades... só que só tem 4 no
estoque. Se o banco deixasse isso acontecer, entraria em estado inconsistente — ou seja, quebrado.
Resultado? A transação é cancelada e o banco volta ao último estado válido. Simples assim! Então, qual
é o papel da consistência aqui?

A consistência garante que o banco comece em um estado consistente; a transação só será concluída se,
ao final, o banco continuar consistente; se der qualquer problema no meio, o sistema volta ao estado
anterior, que era válido. É como se a consistência fosse o “fiscal do banco”, sempre garantindo que
nenhuma transação vai deixar o sistema maluco.

Isso é essencial em áreas críticas — como bancos, hospitais, companhias aéreas, serviços públicos. Já
pensou um hospital com informações inconsistentes de prontuário? Ou um banco onde você tem saldo
negativo sem nunca ter feito saque? É o tipo de coisa que não pode acontecer de jeito nenhum. Outro
ponto importante: consistência é uma parceria entre o sistema e o projeto do banco. O SGBD ajuda, mas
quem define as regras somos nós, ao desenhar o banco e programar as transações. O sistema precisa
saber o que é considerado “válido” — senão, não tem consistência para garantir.

Isolamento
Vamos falar agora sobre isolamento, a terceira letrinha do modelo ACID. Esse princípio é especialmente
importante em ambientes multiusuários, ou seja, quando várias pessoas ou sistemas estão usando o
banco de dados ao mesmo tempo. Veja bem: o isolamento serve para garantir que, mesmo que várias
transações estejam sendo executadas ao mesmo tempo, uma não atrapalhe a outra. É como se cada
transação estivesse em uma salinha separada, sem espiar o que a outra está fazendo. E por que isso é tão
importante? Porque sem esse cuidado, a chance de dar ruim é grande.

Vamos imaginar uma situação no sistema de um banco. Suponha que duas pessoas estejam tentando
transferir dinheiro da mesma conta — ao mesmo tempo. Se o banco não cuidar direitinho disso, pode
acontecer de o saldo ser calculado errado; alguém receber duas vezes; ou até o dinheiro “sumir”. Aí já viu
o prejuízo, né? Aí que entra o isolamento: o banco de dados garante que cada transação só veja dados
de outras transações que já foram concluídas com sucesso (o famoso committed).

Isso evita problemas como: leitura suja (ler dados que ainda podem ser desfeitos), leitura não repetível (o
dado muda entre uma leitura e outra dentro da mesma transação) ou leitura fantasma (uma nova linha
aparece “do nada” porque outra transação a inseriu no meio do caminho). Para conseguir isso, os SGBDs
usam algumas técnicas, como: bloqueios (trava aqui, destrava ali), controle de concorrência otimista
(confia que vai dar tudo certo, e só no final checa se houve conflito) ou versão múltipla de dados (MVCC),
que é como manter várias versões do mesmo dado.

Durabilidade
Chegamos ao último pilar do modelo ACID: a Durabilidade — aquela que garante que, uma vez que uma
transação foi concluída com sucesso, ela não se perde nunca mais. Pode acabar a luz, o servidor pode
travar, o computador pode explodir (ok, exagero) — mas o que foi salvo, está salvo! Veja bem: quando
você finaliza uma compra online e aparece aquela telinha “compra confirmada”, você confia que: o
pedido foi registrado, o estoque foi atualizado e o seu cartão foi devidamente debitado.

Agora, imaginem o caos se o sistema simplesmente esquecesse que você comprou, só porque o servidor
caiu dois segundos depois? Pois é, o princípio da durabilidade é o que impede esse tipo de tragédia.
Mas como os SGBDs garantem isso? Eles usam uma técnica chamada log de transações. Antes de aplicar
qualquer mudança real no banco de dados, o sistema escreve tudo em um arquivo de log. É tipo um
diário das operações que aconteceram. Se algo der errado no meio do caminho, o sistema pode “ler o
diário” e refazer as transações com sucesso quando voltar ao ar.

Além disso, entram em cena recursos como: checkpoints (salvamentos automáticos do estado do banco),
espelhamento de dados (cópias sincronizadas) e backups automáticos, claro. Tudo isso ajuda a garantir
que, se uma transação foi confirmada, ela está segura. E essa segurança é fundamental em áreas onde
não dá para brincar com dados, como bancos, lojas online, hospitais, companhias aéreas, entre outros.
Imaginem perder a confirmação de um pagamento ou o histórico de um paciente?

Um excelente caso de uso para ilustrar as quatro propriedades ACID de uma transação é a
transferência de dinheiro entre contas bancárias. Imagine que João deseja transferir R$ 1.000,00 de
sua conta para a conta de Maria. Essa operação, apesar de parecer simples para o usuário, envolve
uma série de processos internos que precisam garantir integridade absoluta no banco de dados.
Vejamos como as propriedades atuam:

1. Atomicidade: a transferência só pode ter dois resultados – ou ocorre completamente, ou não
ocorre absolutamente nada. Isso significa que o valor deve ser debitado da conta de João e
creditado na conta de Maria. Se por algum motivo o crédito na conta de Maria falhar (ex.: queda de
energia ou erro de rede), o sistema cancela o débito feito em João. A operação é indivisível — tudo
ou nada.

2. Consistência: após a transação, o banco de dados deve permanecer em um estado válido. Isso
significa que, antes e depois da transferência, as regras do sistema (como saldos não negativos ou
somatório total do dinheiro nas contas) devem ser respeitadas. Se João tinha R$ 2.000 e Maria R$
3.000, após a transação os saldos devem ser R$ 1.000 e R$ 4.000 — sem perda ou criação de dinheiro
no processo.

3. Isolamento: suponha que, ao mesmo tempo que João faz essa transferência, outro cliente esteja
pagando uma conta com débito direto na conta de Maria. O SGBD deve isolar as transações para
que elas não interfiram uma na outra. Ou seja, cada uma "age como se fosse única no sistema",
evitando que valores sejam lidos ou escritos com base em dados ainda não confirmados por outras
transações em andamento.

4. Durabilidade: depois que a transferência é concluída e o sistema confirma a operação para o
usuário, o resultado deve ser permanente (também chamado de persistente). Mesmo que o sistema
do banco de dados caia segundos depois, ao reiniciar, os saldos de João e Maria devem refletir a

                                          Independência dos Dados
Quando estamos falando sobre independência de dados, estamos tratando da capacidade de
modificar a definição dos esquemas de determinado nível, sem afetar o esquema de nível
superior. Existem dois níveis de independência de dados: a independência física e a independência
lógica. Ressalto que se um sistema de banco de dados provê independência física dos dados, não
se pode inferir que esse sistema também provê independência lógica de dados.

 Independência Lógica dos Dados

A independência lógica dos dados trata da capacidade de alterar o esquema conceitual sem
precisar modificar os esquemas externos ou programas/aplicações. O mapeamento nível
externo para o conceitual é a chave para a independência lógica de dados.

 Independência Física dos Dados

A independência física dos dados trata da capacidade de alterar o esquema interno sem ter de
alterar o esquema conceitual. O mapeamento nível conceitual para o interno é a chave para a
independência física de dados.


     (AL/MT – 2013) A capacidade de alterar o esquema conceitual, sem que seja necessário
     alterar os esquemas externos ou os programas de aplicação, é denominada:

     a) independência lógica de dados.
     b) independência física de dados.
     c) independência interna de dados.
     d) fragmentação de dados.
     e) transparência de dados.
     _______________________
     Comentários: essa é a definição de independência lógica de dados, isto é, capacidade de modificar o esquema conceitual sem
     a necessidade de reescrever os programas aplicativos. (Letra A).




     (MEC – 2011) Independência de dados é a capacidade de modificar a definição dos
     esquemas de determinado nível, sem afetar o esquema de nível superior. Existem dois
     níveis de independência de dados: a independência física e a independência lógica.
     _______________________
     Comentários: a independência realmente trata da capacidade de modificar a definição de esquemas de determinado nível, sem
     afetar o esquema de nível superior. Ademais, temos dois tipos: independência física e independência lógica (Correto).

                                    abstração por meio de modelos que veremos a seguir: Modelo
                                    Conceitual, Modelo Lógico e Modelo Físico.

Modelo Conceitual (ou Modelo de Alto Nível)

Oferece conceitos que são mais próximos ao modo como
muitos usuários compreendem os dados. Ele utiliza
conceitos como entidades, atributos e relacionamentos. Em
geral, é utilizado para envolver o cliente e discutir os aspectos
do negócio e, não, da tecnologia, visto que não há limitações
ou tecnologias específicas. Esse modelo é independente de
hardware ou software, podendo ser implementado por
qualquer SGBD – é possível desenhá-lo e implementá-lo em
qualquer SGBD disponível no mercado (Ex: MER).

Modelo Lógico (ou Modelo de Implementação ou Representativo)

                                                Também chamado de Modelo Representativo, o
                                                modelo lógico oferece conceitos que podem ser
                                                facilmente entendidos pelos usuários finais, mas que
                                                não está muito longe do modo como os dados são
                                                organizados e armazenados no computador. Em geral,
                                                eles ocultam muitos detalhes do armazenamento de
                                                dados em disco, mas podem ser implementados
                                                diretamente em um sistema de computador.

                                                Nesse caso, ele constitui uma representação para um
                                                banco de dados específico, utilizando as estruturas
                                                suportadas por ele. Logo, o modelo lógico depende do
                                                tipo particular de Sistema Gerenciador de Banco de Dados
                                                utilizado (Ex: Modelo Relacional).

Na verdade, as estruturas para armazenamento de dados e os métodos de acesso ao banco de dados

2. (CESPE / SEPLAN-RR - 2023) Atomicidade, uma das propriedades cruciais em transações de banco
   de dados relacional, é a chave para manter os dados precisos no banco de dados e garantir que eles
   estejam em conformidade com regras, regulamentos e políticas da empresa.

Comentários:

Perfeito! A atomicidade desempenha um papel crucial nas transações de banco de dados relacional,
garantindo que os dados sejam precisos, consistentes e estejam em conformidade com as regras e
políticas da empresa.

Diego, por que não pode ser Consistência? Tanto atomicidade quanto a consistência tratam da
integridade dos dados. A frase realmente menciona que a propriedade garante que os dados estejam
precisos e sigam regras, regulamentos e políticas da empresa. No entanto, o contexto sugere que a
questão está enfatizando que a transação ocorra por inteiro ou não ocorra, o que caracteriza Atomicidade.
Se o foco fosse evitar que regras fossem quebradas (Ex: saldo negativo, chave estrangeira inválida), então
seria Consistência. Como a questão trata da transação ser executada por completo ou revertida, trata-se
de Atomicidade.

                                                                                       Gabarito: Correto

3. (CESPE / AGER-MT - 2023) Assinale a opção em que é apresentada a propriedade envolvida quando
   uma transação de banco de dados é completada com sucesso e as mudanças que ela fez no banco
   persistem, mesmo que existam falhas no sistema:

   a) atomicidade
   b) consistência
   c) isolamento
   d) durabilidade
   e) inconsistência de dados.

Comentários:

A propriedade envolvida quando uma transação de banco de dados é completada com sucesso e as
mudanças que ela fez no banco persistem, mesmo que existam falhas no sistema, é a durabilidade. Ela
assegura que, uma vez que uma transação seja confirmada (completada com sucesso) e suas mudanças
sejam gravadas no banco de dados, essas alterações sejam permanentes, mesmo que ocorram falhas
subsequentes, como falta de energia, falha de hardware ou problemas de software. Em outras palavras,
as alterações devem ser duráveis e não podem ser desfeitas.

É o que? Que viagem foi essa? Um esquema de banco de dados não é uma representação gráfica ou

65.(CESGRANRIO / IPEA - 2024) Considere que, em um banco de dados preparado para persistir dados
   de apoio à realização de estudos na área agropecuária, existem duas tabelas:

       IMÓVEL (cod-sncr, denominacao, cod-mun, area-total)
       MUNICÍPIO (cod-mun, uf, qtd-imoveis)

   A chave primária de um imóvel é o seu código no Sistema Nacional de Cadastro Rural (SNCR), e a de
   um município é o seu código, segundo o IBGE. A coluna IMÓVEL.cod-mun é chave estrangeira e
   referencia MUNICÍPIO.cod-mun.

   Uma aplicação, ou sistema, realiza regularmente a seguinte transação nesse banco de dados:

       Início da transação
       Inserção dos dados de um novo imóvel na tabela IMÓVEL
       Atualização de qtd-imoveis na tabela MUNICÍPIO
       Commit

   Nesse exemplo, a propriedade de atomicidade de uma transação garantirá que:

   a) a integridade referencial entre as duas tabelas sempre será mantida.
   b) apenas usuários autorizados poderão consultar os novos dados inseridos.
   c) nenhuma das duas tabelas será modificada em caso de problema durante a sua execução.
   d) não existirão dois municípios com o mesmo código.
   e) não haverá deadlock entre duas transações concorrentes.

Comentários:

(a) Errado. A integridade referencial é assegurada pelo sistema de gerenciamento de banco de dados
através da definição de chaves estrangeiras e não é uma garantia direta da atomicidade. A atomicidade
se refere à execução completa da transação ou sua total ausência, mas não garante por si só a integridade
referencial;

(b) Errado. O controle de acesso e autorização para consulta de dados é uma questão de segurança e
gerenciamento de permissões no banco de dados, não estando diretamente relacionado à propriedade
de atomicidade de uma transação;

(c) Correto. A propriedade de atomicidade de uma transação assegura que todas as operações dentro
da transação são completadas com sucesso; caso contrário, se ocorrer algum problema, a transação é
inteiramente revertida (rollback), evitando que alterações parciais sejam aplicadas. Isso significa que, se
houver algum problema durante a execução da transação descrita, nenhuma das duas tabelas (IMÓVEL
e MUNICÍPIO) será modificada, mantendo a consistência dos dados;

(d) Errado. A prevenção de duplicatas em termos de códigos de municípios é uma questão de definição
de chave primária na tabela MUNICÍPIO, e não uma garantia fornecida pela atomicidade;

(e) Errado. Deadlocks ocorrem quando duas ou mais transações ficam presas em espera circular, cada
uma bloqueando a outra. A propriedade de atomicidade não assegura a prevenção de deadlocks; a
gestão de deadlocks é uma questão de controle de concorrência no SGBD.

86.(CESGRANRIO / IBGE - 2013) Um sistema de banco de dados sofreu uma falha severa devido à perda
   de energia no meio da execução de um comando SQL de UPDATE que alterava milhares de registros.
   Devido às garantias fornecidas pelo SGBD, após o reinício do sistema, a transação de UPDATE foi
   revertida, e o banco de dados voltou ao seu estado original.

   A propriedade ACID usada nesse caso foi o(a):

   a) isolamento
   b) determinismo
   c) consistência
   d) atomicidade
   e) durabilidade

Comentários:

Essa questão é uma pegadinha do examinador para confundir o aluno. A Atomicidade garante que ou a
transação é integralmente executada ou não é nada executada. Se eu transfiro dinheiro para a sua conta,
o banco tem que mostrar um valor de débito na minha conta e um mesmo valor de crédito na sua conta.
A atomicidade garante que não vai haver um débito na minha conta sem um crédito na sua conta.

Já a Durabilidade garante que os efeitos de uma transação em caso de sucesso devem persistir no banco
de dados. Em outras palavras, uma vez que uma transação seja efetivada, o banco tem que persisti-la de
maneira durável. Não basta armazenar os valores de débito/crédito em uma memória volátil que apaga
tudo se acabar a energia – os valores devem ser armazenados de forma que, mesmo que acabe a energia,
o servidor de banco de dados trave, a internet caia ou ocorra algum desastre, os dados devem estar
persistidos ou armazenados de forma não volátil.

Como a questão afirma que ocorreu uma perda de energia no meio da execução de um comando, logo
o comando não foi executado integralmente – portanto, estamos falando de atomicidade.
