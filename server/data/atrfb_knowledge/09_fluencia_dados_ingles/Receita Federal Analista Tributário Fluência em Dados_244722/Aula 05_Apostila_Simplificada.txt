Galera, agora vamos falar sobre Banco de Dados! Vamos ver a definição de banco de dados de
acordo com três dos mais consagrados autores desse tema:

De acordo com C. J. Date:

       Banco de dados é uma coleção de dados persistentes que é utilizada por sistemas de aplicação
       de uma organização, cujo esquema e conteúdo são definidos, organizados e mantidos pelo
       Sistema de Gerenciamento de Banco de Dados (SGBD).

De acordo com Abraham Siberschatz:

       Um banco de dados é uma coleção de dados persistentes, utilizados pelas aplicações de uma
       organização, que são independentes de programas de aplicação e dispositivos de
       armazenamento físico.

De acordo com Ramez Elmasri:

       Um banco de dados é uma coleção de dados relacionados, representando informações sobre um
       domínio específico. Ele é projetado para ser construído, mantido e acessado de forma
       conveniente e eficiente.

No entanto, o uso comum do termo banco de dados normalmente é mais restrito e tem as
seguintes propriedades implícitas:

▪ Propriedade #1: um banco de dados representa algum aspecto do mundo real – algumas
  vezes chamado de Minimundo ou Universo de Discurso. As mudanças no minimundo são
  refletidas no banco de dados;

▪ Propriedade #2: um banco de dados é uma coleção logicamente coerente de dados inter-
  relacionados com algum significado inerente. Galera, se você tiver uma variedade aleatória de
  dados, você não tem um banco de dados;

▪ Propriedade #3: um banco de dados é projetado, construído e populado com dados para uma
  finalidade específica. Possui um grupo definido de usuários e algumas aplicações específicas
  nas quais esses usuários estão interessados.

A definição ficou mais clara agora? Um banco de dados representa algum aspecto do mundo real
por meio de dados logicamente relacionados para uma finalidade específica. Quando pensamos
em nosso dia a dia, é possível notar que interagimos com bancos de dados o tempo inteiro – desde
quando sacamos dinheiro em um caixa eletrônico até quando compramos um produto em uma loja
online ou visualizamos nossas redes sociais. E o que são dados?

De acordo com o autor Ramez Elmasri, dados são fatos brutos, que podem consistir em números,
palavras, imagens, sons, vídeos ou qualquer forma de informações que ainda não tenham sido
processadas ou organizadas para obter um significado específico. Os dados, por si só, não
possuem contexto ou relevância imediata, sendo apenas representações simbólicas de eventos,
entidades ou conceitos.

A transformação dos dados em informações significativas ocorre por meio do processo de
organização, interpretação e análise, geralmente realizado por sistemas de gerenciamento de
banco de dados para fornecer suporte à tomada de decisões e à execução de tarefas. Ainda de
acordo com Elmasri, a complexidade e o tamanho dos bancos de dados como considerações
importantes no projeto e gerenciamento de sistemas de banco de dados.

▪ Complexidade: a complexidade de um banco de dados está relacionada à quantidade e
  variedade de informações que ele armazena, bem como às relações e interações entre os dados.
  Bancos de dados complexos podem envolver várias tabelas, relacionamentos complexos,
  restrições de integridade e processos de recuperação avançados. A complexidade aumenta os
  desafios do projeto, implementação e manutenção do banco de dados.

▪ Tamanho: o tamanho de um banco de dados se refere à quantidade de dados armazenados no
  sistema. Elmasri destaca que o tamanho dos bancos de dados pode variar amplamente, desde
  pequenos conjuntos de dados até enormes volumes de informações. Ele enfatiza que o tamanho
  do banco de dados pode impactar a capacidade de armazenamento, desempenho, eficiência e
  custo de gerenciamento do sistema.

Outra característica importante é que bancos de dados podem ser gerados e mantidos de forma
manual ou computadorizada. A geração e manutenção manual de bancos de dados envolvem o
uso de técnicas tradicionais, nas quais os dados são inseridos, atualizados e consultados por meio
de interações humanas diretas. Esse processo pode incluir a criação de tabelas, definição de
esquemas, inserção de registros e realização de consultas utilizando comandos de consulta.

Por outro lado, a geração e manutenção computadorizada de bancos de dados envolvem o uso de
Sistemas de Gerenciamento de Banco de Dados (SGBDs), que automatizam muitas das tarefas
relacionadas ao gerenciamento de dados. Os SGBDs fornecem interfaces e linguagens de consulta
que permitem aos usuários definir a estrutura do banco de dados, inserir e atualizar os dados de
forma eficiente, realizar consultas complexas e gerenciar a segurança e integridade dos dados.

Vamos resumir: um banco de dados é uma coleção de dados logicamente relacionados que
representam algum aspecto do mundo real, podendo ter qualquer tamanho e complexidade, e

Características de Banco de Dados
                                                                                           INCIDÊNCIA EM PROVA: baixa


Diversas características distinguem a abordagem de banco de dados da técnica muito mais antiga
de escrever programas customizados para acessar os dados armazenados em arquivos. No
processamento de arquivo tradicional, cada usuário define e implementa os arquivos necessários
para uma aplicação específica como parte da programação da aplicação. Por exemplo: um usuário,
o departamento de registro acadêmico, pode manter arquivos sobre os alunos e suas notas.

Os programas para imprimir o histórico do aluno e entrar com novas notas são implementados
como parte da aplicação. Um segundo usuário, o departamento de finanças, pode registrar as
mensalidades dos alunos e seus pagamentos. Embora os dois usuários estejam interessados em
dados sobre os alunos, cada usuário mantém arquivos separados — e programas para manipular
esses arquivos —, pois cada um requer algum dado não disponível nos arquivos do outro usuário.

Essa redundância na definição e no armazenamento de dados resulta em espaço de
armazenamento desperdiçado e em esforços redundantes para manter os dados comuns
atualizados. Na abordagem de banco de dados, um único repositório mantém dados que são
definidos uma vez e depois acessados por vários usuários, repetidamente, por meio de
consultas, transações e programas de aplicação.

As principais características da abordagem de banco de dados versus a abordagem de
processamento de arquivos são as seguintes:

Natureza de autodescrição de um sistema de banco de dados

A palavra “autodescrição” já dá a dica! Os bancos de dados não contêm apenas dados – eles
contêm também uma definição ou descrição completa da estrutura e restrições desses dados.
Então, se ele armazena uma tabela com dados sobre as notas de um aluno, ele também armazenará
os dados sobre essa tabela. Que dados, professor? Ele armazena qual o nome da tabela, o nome de
suas colunas, o tamanho de cada coluna, entre outros.

Isolamento entre programas e dados, e abstração de dados

Vocês se lembram da imagem de algumas páginas atrás em que nós definimos Aplicações, SGBD e
Banco de Dados? Pois é, tudo separado bonitinho! No processamento de arquivos, as aplicações
eram misturadas com a estrutura de arquivos. É por essa razão que dizemos que há um
isolamento entre programas e dados. Se você modifica suas aplicações, não interfere nos dados;
se você modifica seus dados, não interfere nas aplicações. Prosseguindo...

Vocês sabem o que quer dizer abstração? Essa é uma palavra muito comum na área de tecnologia da
informação e é bom que vocês saibam responder de bate-pronto: abstração é a subtração de
detalhes. Como consequência, podemos concluir que quanto mais abstrato, menos detalhes; e
quanto menos abstrato, mais detalhes. A seguir temos uma imagem aérea da Catedral de Brasília.
Pergunta: qual delas é mais abstrata? Da direita! Por quê? Porque tem menos detalhes.

A característica que permite a independência de dados da aplicação e a independência da
operação da aplicação é chamada de abstração de dados. Um SGBD oferece aos usuários uma
representação conceitual de dados que não inclui muitos dos detalhes de como os dados são
armazenados ou como as operações são implementadas. De maneira informal, um modelo de
dados é uma abstração de dados usada para oferecer essa representação conceitual.




A abstração é a base para se conseguir o isolamento entre programas e dados. Por quê? Porque a
aplicação não precisa de detalhes do SGBD – ela precisa apenas de uma interface. Pensando em
um exemplo mais grosseiro: quando você quer que os correios façam uma entrega para outra

Suporte de Múltiplas Visões de Dados

Pessoal, eu falei para vocês que o banco de dados funciona como um repositório central de dados –
diferente dos arquivos. Dessa forma, é possível que várias aplicações tentem acessá-lo e cada
uma pode ter uma necessidade diferente. Imagine que uma determinada aplicação não precise
visualizar toooodos os dados – pode ser que ela precise acessar apenas alguns. Logo, nós podemos
afirmar que aplicações diferentes exigem pontos de vista ou visões diferentes do banco.

Uma visão (ou view) é, em geral, um subconjunto do banco de dados. Dessa forma, se você deseja
visualizar apenas uma parte dos dados de uma tabela, você pode criar uma visão personalizada
apenas para a sua aplicação ou para um conjunto de usuários. Eu sei que isso pode não estar tão
claro agora, mas ficará mais claro quando prosseguirmos com a teoria. Guardem apenas que um
banco de dados oferece suporte a múltiplas visões de dados.

Compartilhamento de Dados e Processamento de Transação

Um SGBD multiusuário é todo aquele SGBD que suporta que múltiplas aplicações – também
chamadas de usuários – acessem o banco de dados ao mesmo tempo. Galera, isso é essencial se o
dado para múltiplas aplicações estiver sendo mantido em um único banco de dados. O SGBD
precisa incluir um software de controle de concorrência para garantir que vários usuários
interajam simultaneamente com o banco de dados sem problemas.

Imagine a seguinte situação hipotética: o departamento de finanças e o departamento pedagógico
da escola tem acesso a mesma tabela de dados pessoais dos alunos. Concordam? Agora imaginem
que José, do Departamento de Finanças, tente atualizar um dado pessoal ao mesmo tempo
que Maria, do Departamento Pedagógico, também tenta atualizar exatamente o mesmo dado.
O que vai acontecer? Merd#%@, professor! Nada! Nadica de nada...

Sabe por quê? Porque o SGBD possui um software de controle de concorrência para garantir que
vários usuários tentando atualizar o mesmo dado façam isso de uma maneira controlada, de modo
que o resultado dessas transações seja correto. Imagine você tentando reservar o assento na janela
em um voo internacional ao mesmo tempo que outra pessoa esteja tentando reservar o mesmo
assento. O SGBD garante que operações concorrentes operem de maneira correta!

De acordo com outro doutrinador (C. J. Date), uma abordagem de banco de dados possui os
seguintes benefícios: o dado pode ser compartilhado; a redundância pode ser reduzida;
inconsistências podem ser evitadas; pode-se utilizar o suporte a transações; a integridade pode ser
mantida; a segurança pode ser aperfeiçoada; requisitos conflitantes podem ser balanceados; e
padrões podem ser utilizados.

Vamos ver sua definição de acordo com nossos autores favoritos:

De acordo com C. J. Date:

       Uma transação é uma unidade de programa de usuário que trata do acesso e possivelmente da
       atualização do banco de dados. Uma transação é uma sequência de uma ou mais ações
       (operações) de acesso ao banco de dados, como leitura, gravação, exclusão, inserção, etc.

De acordo com Abraham Siberschatz:

       Uma transação é uma sequência de ações executadas como uma unidade indivisível de trabalho.
       Uma transação pode realizar várias operações de banco de dados, como leitura e gravação, e

De acordo com Ramez Elmasri:

       Uma transação é uma sequência de operações de banco de dados que é tratada como uma
       unidade indivisível de trabalho. Ela representa uma tarefa lógica completa realizada por um
       usuário/aplicação, envolvendo a leitura e/ou modificação dos dados armazenados.

Em suma, uma transação é um programa em execução ou processo que inclui um ou mais
acessos ao banco de dados, como fazer a leitura de dados ou inserir, excluir e atualizar dados
do banco. Ela executa um acesso logicamente correto a um banco de dados quando ela é executada
de forma completa e sem interferência de outras transações. Elas possuem quatro propriedades
importantíssimas:

Atomicidade

Essa propriedade indica que uma transação é uma unidade indivisível de trabalho, onde todas
as suas operações são tratadas como uma única entidade. Se uma operação falhar em qualquer
momento, todas as operações da transação são desfeitas e o banco de dados retorna ao estado
anterior à transação. A atomicidade em transações de banco de dados pode ser explicada por meio
de uma analogia com uma transferência bancária.

Imagine que você precisa transferir dinheiro de uma conta para outra. A atomicidade garante que
a transferência seja tratada como uma operação indivisível, ou seja, ou ela é realizada
completamente ou não é realizada de forma alguma. Analogamente, pense na transferência

bancária como uma transação. Durante essa transação, duas ações são executadas: a retirada de
dinheiro da conta de origem e o depósito na conta de destino.

A atomicidade garante que essas ações ocorram em conjunto, de forma que se uma delas
falhar, a transação inteira é revertida e nenhuma modificação é feita no banco de dados. Por
exemplo, se ocorrer um problema técnico durante a transferência, e o dinheiro for retirado da conta
de origem, mas não for depositado na conta de destino, a atomicidade garante que a transação seja
revertida, e o dinheiro seja devolvido à conta de origem.

Isso evita que o banco de dados fique em um estado inconsistente, onde parte da transação foi
realizada e a outra não. Dessa forma, a atomicidade assegura que as operações de uma
transação sejam tratadas como uma unidade indivisível, garantindo a consistência e a
integridade do banco de dados. Quando uma transação é desfeita, dizemos que houve um rollback
e quando uma transação é confirmada, dizemos que houve um commit.

Consistência

Essa propriedade garante que uma transação leva o banco de dados de um estado consistente
para outro estado consistente. Isso significa que as restrições de integridade 3 definidas no banco
de dados são mantidas durante a execução da transação, preservando a validade e a coerência dos
dados. A consistência em transações de banco de dados pode ser explicada por meio de uma
analogia com a montagem de um quebra-cabeça.

Imagine que você está montando um quebra-cabeça com várias peças. Cada peça representa um
dado ou uma informação no banco de dados. A consistência garante que todas as peças estejam
corretamente encaixadas, formando uma imagem completa e sem contradições. Analogamente,
pense na montagem do quebra-cabeça como uma transação no banco de dados. Durante essa
transação, várias operações são executadas para inserir, atualizar ou excluir dados.

A consistência garante que, ao final da transação, o banco de dados esteja em um estado
coerente e livre de contradições. Por exemplo, se uma operação atualiza um dado em uma tabela
e outra operação tenta ler esse dado ao mesmo tempo, a consistência garante que a leitura só
ocorra após a atualização estar concluída. Isso evita que a leitura seja feita com dados
desatualizados ou inconsistentes.

Da mesma forma, a consistência garante que as restrições e regras definidas para os dados sejam
obedecidas. Por exemplo, se uma transação tentar inserir um novo registro que viole uma restrição
de integridade, como uma chave primária duplicada, a consistência garante que a transação seja
abortada e o banco de dados permaneça consistente. Ela garante que operações sejam realizadas
de forma que o banco de dados mantenha um estado coerente, sem violações de restrições.

Isolamento

Essa propriedade garante que o resultado de uma transação seja invisível para outras
transações em execução simultaneamente. Cada transação é executada de forma isolada, como
se fosse a única transação em execução, evitando interferências ou efeitos colaterais indesejados
causados por transações concorrentes. Para entender isso melhor, vamos imaginar uma sala de
estudo em uma biblioteca.

Nessa sala, várias pessoas estão estudando em suas respectivas mesas. Cada pessoa está focada
em seu próprio trabalho, lendo, escrevendo e pesquisando. No entanto, mesmo que estejam no
mesmo ambiente, cada pessoa está isolada em sua própria mesa, sem interferências ou acesso aos
materiais ou anotações de outras pessoas. Da mesma forma, o isolamento refere-se à capacidade
de garantir que as transações ocorram independentemente umas das outras.

Cada transação é como uma pessoa em sua mesa de estudo, realizando suas operações no banco
de dados sem afetar as operações de outras transações. O isolamento garante que as transações
sejam executadas de forma independente, sem interferências ou conflitos, preservando a
integridade e consistência dos dados. Para finalizar, agora vamos ver a última propriedade de uma
transação: durabilidade.

Durabilidade

Essa propriedade assegura que os resultados de uma transação confirmada sejam permanentes
e persistam mesmo em caso de falhas subsequentes do sistema. Após o término bem-sucedido
de uma transação, suas alterações são armazenadas de forma permanente no banco de dados e
não podem ser perdidas. Para entender melhor essa propriedade, vamos imaginar que você está
escrevendo um livro e salvando-o em seu computador.

Ao final de cada dia de trabalho, você faz uma cópia de backup do livro e armazena em um local
seguro, como uma gaveta trancada. Mesmo que ocorra algum problema com o seu computador,
como uma falha de energia ou uma pane no sistema, você pode ter a tranquilidade de que o seu
trabalho está protegido e pode ser recuperado a partir do backup. Essa analogia ilustra o
conceito de durabilidade em um banco de dados.

Durabilidade refere-se à capacidade de garantir que as alterações feitas em um banco de dados
sejam permanentes, mesmo em caso de falhas ou interrupções. Assim como você armazena o
backup do seu livro em um local seguro, no banco de dados, as alterações realizadas em transações
concluídas são registradas de forma persistente em disco ou outro meio de armazenamento
durável.

Três das quatro características importantes que vimos sobre a abordagem de banco de dados são
(1) uso de um catálogo para armazenar a descrição (esquema) do banco de dados de modo a torná-
lo autodescritivo, (2) isolamento de programas e dados (independência entre dados e operação do
programa) e (3) suporte para múltiplas visões do usuário. Para ajudar a alcançar e visualizar essas
características, foi proposto a Arquitetura ANSI/SPARC (ou Arquitetura de Três Esquemas).

A Arquitetura ANSI/SPARC se divide em três níveis independentes: externo, conceitual e interno.
Antes de entrarmos nos detalhes de cada um, vamos entender primeiramente o que é um esquema
e o que é uma instância de um banco de dados. Falando de maneira bem simples, um esquema é
uma descrição da estrutura de um banco de dados. Em outras palavras, ele se refere à forma como
os dados são armazenados, organizados e relacionados entre si.

O esquema descreve a estrutura das tabelas, os tipos de dados dos campos, as chaves primárias
e estrangeiras, as restrições de integridade e outras informações importantes para representar
e manipular os dados de forma coerente. Imagine que você está construindo uma casa: o esquema
seria equivalente ao projeto arquitetônico da casa, que define a estrutura, layout e características
principais.

Ele descreve os cômodos, os tipos de materiais a serem usados, as dimensões das janelas e portas,
o posicionamento dos móveis, entre outros detalhes importantes. O esquema da casa fornece uma
representação abstrata do projeto, permitindo que você entenda como a casa será construída e
como os elementos se relacionam entre si. Ele serve como um guia para os construtores, arquitetos
e outros profissionais envolvidos na construção, garantindo que todos sigam um plano comum.

Da mesma forma, em um banco de dados, o esquema descreve a estrutura lógica dos dados,
especificando as tabelas, os campos, os relacionamentos e outras características. Ele funciona
como um projeto que orienta a criação e o uso do banco de dados, garantindo consistência e
coerência na manipulação dos dados. O esquema de um banco de dados, portanto, é análogo ao
projeto arquitetônico de uma casa.

Em outras palavras, assim como o projeto arquitetônico da casa é usado como referência durante a
construção e manutenção da mesma, o esquema de um banco de dados é usado como base para
projetar, desenvolver e gerenciar o banco de dados de forma consistente ao longo do tempo. Já
uma Instância (ou Estado) é o conjunto de dados armazenados no banco e um determinado
momento de operação.

Trata-se da representação dos dados armazenados no banco de dados em um determinado
instante de tempo. Podemos entender uma instância de banco de dados como um instantâneo
dos dados contidos no banco de dados em um determinado momento. Ela representa o conjunto
de valores e relacionamentos atualmente presentes nas tabelas e outros objetos do banco de
dados. Por exemplo, considere um banco de dados de uma loja online.

A instância pode incluir informações como a lista de produtos disponíveis, os pedidos feitos pelos
clientes e os estoques atuais. Esses dados estão em conformidade com o esquema do banco de
dados, ou seja, seguem a estrutura definida pelos tipos de tabelas, colunas e relacionamentos
especificados no esquema. À medida que ocorrem operações de inserção, atualização ou exclusão
de dados, a instância do banco de dados é modificada, refletindo o estado mais recente dos dados.

Cada vez que os dados são alterados, uma nova instância é gerada para refletir as atualizações
feitas. Logo, a instância de banco de dados é a representação concreta dos dados armazenados
em um banco de dados em um determinado momento, enquanto o esquema descreve a
estrutura lógica e as regras de organização dos dados no banco de dados. Pronto! Agora estamos
melhor preparados para entender a Arquitetura ANSI/SPARC.

Nível Externo
Também conhecido como Nível de Visão ou Nível Lógico do Usuário é o mais próximo dos
usuários – ou seja, é aquele que se ocupa do modo como os dados são vistos ou percebidos por
usuários individuais. A maior parte dos usuários não está interessada no banco de dados inteiro,
mas somente em alguma parte restrita dele; assim, haverá muitas visões externas distintas, cada
qual consistindo em uma representação mais ou menos abstrata de alguma parte do banco.

A visão que um usuário tem dessa parte será um tanto abstrata quando comparada com como os
dados são fisicamente armazenados. Os níveis externo e conceitual são níveis de modelo, enquanto
o nível interno é um nível de implementação; em outras palavras, os níveis externo e conceitual são
definidos em termos de construções voltadas para o usuário, como registros e campos, enquanto o
nível interno é definido em termos de construções voltadas para a máquina, como bits e bytes.

Essa visão externa do usuário é o conteúdo do banco de dados visto por determinado usuário – para

Nível Conceitual

Também conhecido como Nível Lógico de Comunidade (ou apenas Nível Lógico), é um nível
indireto entre os níveis interno e externo. A visão conceitual é uma representação de todo o
conteúdo de informações do banco de dados, mais uma vez (como no caso de uma visão externa)
em uma forma um tanto abstrata, em comparação com o modo como os dados são armazenados
fisicamente.

Em geral, ela também será bastante diferente do modo como os dados são visualizados por
qualquer usuário em particular. Trata-se de uma maneira de descrever a estrutura do banco de
dados inteiro para uma comunidade de usuários, isto é, quais dados são armazenados em todo o
banco de dados e como os dados estão inter-relacionados. Esse nível oculta os detalhes das
estruturas de armazenamento físico e se concentra na descrição de entidades.

O nível conceitual faz uma ponte entre o nível externo e o nível interno por meio de um
mapeamento conceitual/interno de dados. O nível externo descrevia apenas parte do banco de
dados; já o nível conceitual descreve todo o banco de dados e se concentra em definir quais
dados estão armazenados e quais são as relações entre esses dados. Agora finalmente podemos
estudar o nível interno...

Nível Interno

Também conhecido como Nível de Armazenamento ou Nível Físico, é o meio mais próximo do
meio de armazenamento físico, isto é, aquele que se ocupa com o modo como os dados estão
fisicamente armazenados no banco de dados e no hardware do computador – além da definição
das estruturas físicas que permitem obter um desempenho satisfatório. Ele descreve os detalhes
completos do armazenamento de dados e dos caminhos de acesso para o banco de dados.

A visão interna é uma representação de baixo nível do banco de dados por inteiro; ela consiste em
muitas ocorrências de cada um dos vários tipos de registros internos. Ela está mais longe dos
usuários e mais próximo do banco de dados – cuidando da representação física em que os
registros são armazenados. Saiba que existe apenas um esquema interno para um único esquema
conceitual para várias visões externas. Ok?

Um mapeamento é o processo de associação entre elementos de um conjunto de dados para outro
conjunto de dados. O mapeamento externo/conceitual traduz visões externas para a visão
conceitual, garantindo a adequação e coerência entre as diferentes perspectivas do banco de
dados. Isso permite que os usuários tenham uma representação compreensível e consistente dos
dados, independentemente das suas necessidades e formas de acesso.

Já o mapeamento conceitual/interno é o processo de traduzir a visão lógica e abstrata do banco
de dados (nível conceitual) em uma representação física e de baixo nível que possa ser armazenada
e manipulada pelo SGBD (nível interno). Ele assegura que a estrutura e as regras definidas no nível
conceitual sejam adequadamente refletidas na implementação física do banco de dados. Em regra,
o mapeamento externo/conceitual ocorre após o mapeamento conceitual/interno.


                                                   analogia
Por fim, vamos utilizar uma analogia para resumir a Arquitetura ANSI/SPARC. Imagine uma
biblioteca com um vasto acervo de livros. A biblioteca possui uma equipe de funcionários que
trabalha em diferentes departamentos, cada um desempenhando um papel específico no
funcionamento da biblioteca. Na Arquitetura ANSI/SPARC, a biblioteca como um todo é o sistema
de banco de dados, e cada departamento representa um componente da arquitetura.

O Departamento de Catalogação é responsável por organizar e classificar os livros de acordo com
um sistema padronizado. Isso seria equivalente ao nível conceitual, que define a estrutura e
organização dos dados no banco de dados. O Departamento de Armazenamento é encarregado de
armazenar os livros nas prateleiras de acordo com as categorias definidas pelo Departamento de
Catalogação.

Ele seria equivalente ao nível interno, que descreve como os dados são armazenados fisicamente
em dispositivos de armazenamento. Por fim, o Departamento de Atendimento ao Leitor permite
que os leitores acessem os livros, fornecendo orientações, auxiliando na localização dos livros e
facilitando o empréstimo. Esse departamento representa as visões externas, que são as diferentes
formas pelas quais os usuários podem visualizar e acessar os dados.

Logo, o nível externo é comparável ao catálogo da biblioteca, onde os usuários podem pesquisar
por títulos de livros, autores ou assuntos específicos; o nível conceitual seria como a forma como os
livros estão organizados nas prateleiras da biblioteca; e o nível interno corresponde à forma como
os livros estão fisicamente armazenados nas estantes da biblioteca. O mapeamento
externo/conceitual/interno pode ser comparado à jornada de um usuário da biblioteca.

O usuário consulta o catálogo (mapeamento externo) para encontrar informações sobre um livro
específico. Com base nessas informações, ele navega pelas prateleiras (mapeamento conceitual)
até encontrar o livro desejado. Por fim, o livro é retirado da prateleira (mapeamento interno) para
ser lido. A Arquitetura ANSI/SPARC visa separar claramente esses componentes, permitindo
que o gerenciamento seja mais flexível, seguro, eficiente e independente.

                                      Independência dos Dados
Quando estamos falando sobre independência de dados, estamos tratando da capacidade de
modificar a definição dos esquemas de determinado nível, sem afetar o esquema de nível
superior. Existem dois níveis de independência de dados: a independência física e a independência
lógica. Ressalto que se um sistema de banco de dados provê independência física dos dados, não
se pode inferir que esse sistema também permite independência lógica de dados.

▪ Independência Lógica dos Dados: refere-se à capacidade de alterar a estrutura lógica do banco
  de dados sem afetar os programas de aplicação que o utilizam. Isso significa que as alterações
  na estrutura lógica, como adicionar ou remover tabelas, modificar relacionamentos ou
  atributos, não devem exigir que os programas de aplicação sejam alterados. A independência
  lógica de dados é alcançada por meio do uso de visões, consultas e camadas de abstração que
  separam a estrutura lógica do banco de dados da forma como os dados são manipulados pelas
  aplicações.

▪ Independência Física dos Dados: refere-se à capacidade de alterar a estrutura física do banco
  de dados sem afetar os programas de aplicação ou a estrutura lógica do banco de dados. Isso
  significa que as alterações na forma como os dados são armazenados fisicamente, como a
  alteração do tipo de armazenamento, a reorganização dos dados ou a mudança para um
  servidor diferente, não devem exigir alterações nos programas de aplicação ou na estrutura
  lógica do banco de dados. Ela é alcançada por meio de camadas de abstração, como o SGBD,
  que oculta os detalhes da implementação física do banco de dados dos programas de aplicação.


Projetos de Banco de Dados
                                                                                       INCIDÊNCIA EM PROVA: ALTA


Existe uma outra classificação que também representa a estrutura ou projeto de um banco de dados
em diferentes níveis de abstração – chama-se Projeto de Banco de Dados. Trata-se de um processo
específico de projeto de banco de dados que visa criar um banco de dados eficiente e funcional. Nós
vimos que a Arquitetura ANSI/SPARC é m modelo conceitual que estabelece a estrutura geral do
projeto de banco de dados em três níveis: externo, conceitual e interno.

Já o Projeto de Banco de Dados é um processo específico que abrange a criação de modelos para
implementar um banco de dados eficiente. Nesse caso, também é dividido em três partes, mas
agora dividimos em modelo conceitual, modelo lógico e modelo físico. Cuidado para não confundir
as nomenclatures das duas classificações durante a prova. Embora haja semelhanças entre as
divisões em camadas, as abordagens e os objetivos são diferentes entre esses dois conceitos.

Modelo Conceitual (ou Modelo de Alto Nível)

O modelo conceitual é a representação abstrata e independente de qualquer Sistema
Gerenciador de Banco de Dados específico. Ele descreve os conceitos e as relações entre os dados
de forma geral, sem considerar aspectos técnicos de implementação. O objetivo principal do
modelo conceitual é capturar as regras de negócio, as entidades, os relacionamentos e as restrições
que serão representados no banco de dados.

Esse modelo oferece conceitos que são mais próximos ao modo como muitos usuários
compreendem os dados. Em geral, é utilizado para envolver o cliente e discutir os aspectos do
negócio e, não, da tecnologia, visto que não há limitações ou tecnologias específicas. Nessa
etapa, são utilizados diagramas como o Modelo Entidade-Relacionamento (MER) ou o Modelo de
Dados Orientado a Objetos (MDOO) para representar esses elementos de forma gráfica e intuitiva.

Modelo Lógico (ou Modelo de Implementação ou Representativo)

Também chamado de Modelo Representativo, trata-se de uma adaptação do modelo
conceitual para um tipo específico de SGBD. Ele traduz as entidades, relacionamentos e restrições
do modelo conceitual em estruturas e recursos oferecidos pelo SGBD escolhido. Ele oferece
conceitos que podem ser facilmente entendidos pelos usuários finais, mas que não está muito longe
do modo como os dados são organizados e armazenados no computador.

Em geral, eles ocultam muitos detalhes do armazenamento de dados em disco, mas podem ser
implementados diretamente em um sistema de computador. Nesse caso, ele constitui uma
representação para um banco de dados de um tipo específico, utilizando as estruturas suportadas
por ele. Logo, o modelo lógico depende do tipo particular de SGBD utilizado (Ex: SGBDs
Relacionais, SGBDs Orientados a Objetos, entre outros).

Modelo Físico (ou Modelo Baixo Nível)

O modelo físico é a implementação concreta do banco de dados, especificando os detalhes de
armazenamento, organização dos dados em disco, indexação, otimização de desempenho e
outros aspectos técnicos. Nessa etapa, o modelo lógico é mapeado para a estrutura física do
SGBD. O modelo físico também leva em consideração fatores de desempenho, como o
dimensionamento de hardware, configurações de cache e estratégias de otimização de consultas.

O resultado final do modelo físico é um conjunto de scripts ou comandos que serão executados para
criar o banco de dados no SGBD específico que foi escolhido. Esse modelo oferece conceitos que
descrevem os detalhes de como os dados são armazenados no computador e costumam ser
voltados para especialistas de computadores e, não, para usuários finais. Eu lembro novamente:
esse modelo é totalmente dependente do SGBD.

Vamos utilizar uma analogia para ilustrar a diferença entre os modelos conceitual, lógico e físico no
contexto do projeto de banco de dados. Imagine que você deseja construir uma casa. O modelo
conceitual seria equivalente a um esboço inicial dos principais elementos da casa, como o número
de quartos, banheiros, sala, cozinha, etc. Nessa etapa, você está preocupado principalmente em
definir os requisitos e o layout geral da casa, sem entrar em detalhes técnicos de construção.

O modelo lógico seria como a planta baixa detalhada da casa. Nesse estágio, você traduz o esboço
inicial em um projeto mais concreto, especificando a localização exata dos cômodos, as dimensões,
as conexões entre eles e outros detalhes arquitetônicos. A planta baixa permite que você tenha uma
visão clara da estrutura da casa, mas ainda não aborda aspectos como o tipo de material de
construção ou as cores das paredes.

Por fim, o modelo físico seria como a construção real da casa. Aqui, você considera todos os
detalhes práticos e técnicos envolvidos na construção, como os materiais de construção, os
sistemas elétricos e hidráulicos, o acabamento interno e externo, entre outros. O modelo físico é a
implementação concreta do projeto, onde cada elemento é construído de acordo com as
especificações definidas anteriormente no modelo lógico.

1. (CESPE / SEFAZ-SE – 2022) As técnicas de controle de concorrência são usadas para garantir a
   propriedade de não interferência ou isolamento das transações executadas simultaneamente.
   Algumas das principais técnicas usadas para controlar a execução concorrente de transações
   são baseadas no conceito de bloqueio de itens de dados.

   Considerando os tipos de bloqueios, assinale a opção que contém o esquema de bloqueio que
   possui dois estados — bloqueado e desbloqueado — e que é considerado muito restritivo para
   itens de banco de dados, porque no máximo uma transação pode manter um bloqueio em
   determinado item.

   a) bloqueios compartilhados
   b) bloqueios binários
   c) bloqueios exclusivos
   d) bloqueio em duas fases conservador
   e) bloqueio em duas fases básico

Comentários:

Questão absurdamente aprofundada! Eu acho completamente inviável explicar estratégias de
controle de concorrência em aula. De todo modo, as técnicas de controle de concorrência são
usadas para garantir a propriedade de não interferência ou isolamento das transações executadas
simultaneamente. Um SGBD deve ser capaz de garantir que apenas planos de execução
serializáveis e recuperáveis sejam permitidos e que nenhuma ação de transações efetivadas seja
perdida ao desfazer transações canceladas. Normalmente, um SGBD utiliza um protocolo de
bloqueio para conseguir isso. Bloqueio é um pequeno objeto de controle associado a um objeto do
banco de dados. Protocolo de bloqueio é um conjunto de regras a serem seguidas por transação (e
impostas pelo SGBD) para garantir que, mesmo intercalando as ações de várias transações, o
resultado seja idêntico à execução de todas as transações em alguma ordem serial.

(a) Errado. Bloqueios compartilhados permitem que um item de dado seja acessado por mais de
uma transação para leitura; (b) Correto. Bloqueios binários são simples, mas também muito
restritivos para fins de controle de concorrência e, portanto, não são muito utilizados na prática –
ele pode ter dois estados ou valores: bloqueado e desbloqueado. Se o valor do bloqueio em X for 1,
o item não pode ser acessado. Se for 0, o item pode ser acessado quando solicitado; (c) Errado.
Bloqueios compartilhados são sinônimos de bloqueios exclusivos; (d) Errado. Esse tipo de bloqueio
bloqueia todos os itens aos quais terá acesso, antes de iniciar o seu processamento. Se algum dos
itens não puder ser bloqueado, a transação não bloqueia nenhum item e espera até que todos os
itens estejam disponíveis para bloqueio; (e) Errado. Esse tipo de bloqueio é utilizado para garantir
escalonamentos serializáveis – as operações de bloqueio e desbloqueio nas transações devem
seguir protocolos (Ex: Two-Phase Locking).
